Definición del modelo¶

Se copian los bloques M1 y M0 del enunciado sin cambiar parámetros ni variables. Cada evaluación crea un modelo nuevo. La mediana, la escala y las categorías se aprenden al llamar fit con el train, dentro del Pipeline.

from sklearn.pipeline import Pipeline
from sklearn.compose import ColumnTransformer
from sklearn.impute import SimpleImputer
from sklearn.preprocessing import StandardScaler, OneHotEncoder
from sklearn.linear_model import LogisticRegression
from sklearn.dummy import DummyClassifier
from sklearn.metrics import f1_score, recall_score

NUM = ['distancia_km', 'total_pedido_gtq']
CAT = ['zona', 'categoria_restaurante', 'metodo_pago']
FEATURES = NUM + CAT

def nuevo_modelo():
    """M1. Siempre se crea nuevo; nunca se reutiliza uno ya entrenado."""
    prep = ColumnTransformer([
        ('num', Pipeline([('imp', SimpleImputer(strategy='median')),
                          ('esc', StandardScaler())]), NUM),
        ('cat', OneHotEncoder(handle_unknown='ignore'), CAT),
    ])
    return Pipeline([
        ('prep', prep),
        ('clf', LogisticRegression(max_iter=1000, class_weight='balanced')),
    ])

def entrenar_y_medir(train, test, target='baja'):
    """Entrena M1 con 'train', mide en 'test' y devuelve F1 y recall."""
    m = nuevo_modelo()
    m.fit(train[FEATURES], train[target])
    pred = m.predict(test[FEATURES])
    return {'f1': f1_score(test[target], pred),
            'recall': recall_score(test[target], pred),
            'n_test': len(test),
            'positivos_test': int(test[target].sum())}

def medir_baseline(train, test, target='baja'):
    """M0: modelo "tonto". Predice siempre la clase más común."""
    d = DummyClassifier(strategy='most_frequent')
    d.fit(train[FEATURES], train[target])
    return f1_score(test[target], d.predict(test[FEATURES]))

Pregunta 2. Predicción previa del F1 de M0¶

Hipótesis previa: F1 = 0 si la clase mayoritaria del train es "no baja". Al responder siempre 0, M0 no encuentra verdaderos positivos de la clase 1. Tener muchos aciertos de la clase mayoritaria no implica un buen F1 para detectar las calificaciones bajas. La condición de mayoría se comprueba para cada partición, en lugar de asumirla sin verificar.

# Solo organiza tablas; no cambia los modelos ni las particiones.
def tabla_semillas(resultados):
    tabla = resultados[['semilla', 'n_test', 'positivos_test', 'pct_positivos',
                        'f1', 'f1_baseline', 'recall']].copy()
    tabla.columns = ['Semilla', 'Pedidos test', 'Positivos test', '% positivos',
                     'F1 M1', 'F1 M0', 'Recall M1']
    minimo = {c: tabla[c].min() for c in tabla.columns if c != 'Semilla'}
    maximo = {c: tabla[c].max() for c in tabla.columns if c != 'Semilla'}
    rango = {'Semilla': 'mín - máx', **{
        c: f'{minimo[c]:.4f} - {maximo[c]:.4f}' if c in ['F1 M1', 'F1 M0', 'Recall M1']
        else f'{minimo[c]:.2f} - {maximo[c]:.2f}'
        for c in minimo}}
    return pd.concat([tabla, pd.DataFrame([rango])], ignore_index=True)

def comprobar_particion(train, test):
    assert len(train) > 0 and len(test) > 0
    assert set(train.index).isdisjoint(test.index)
    assert len(train) + len(test) == len(cal)
    assert train.baja.nunique() == 2 and test.baja.nunique() == 2
    assert train.baja.mean() < 0.5, 'M0 ya no respondería siempre no baja.'

registros_splits = []
def registrar_split(nombre, train, test):
    # Se registra el índice original de cada fila para auditar las particiones.
    registros_splits.extend({'experimento': nombre, 'fila_csv': int(i),
                             'pedido_id': int(cal.loc[i, 'pedido_id']), 'conjunto': conjunto}
                            for conjunto, bloque in [('train', train), ('test', test)]
                            for i in bloque.index)

Pregunta 4. Otro grupo obtiene un F1 diferente: ¿quién tiene razón?¶

Ambos resultados pueden ser correctos si usan distintas semillas y reproducen el mismo procedimiento. Si usan las mismas filas, semilla y versiones deberían coincidir; si no, habría que revisar limpieza, orden de filas, variables y ejecución. No realizamos aquí una conversación con otro grupo; esa parte de la actividad debe hacerse en clase.

Para describir la sensibilidad al reparto aleatorio reportaríamos el promedio M1 = 0.1694; M0 = 0.0000, acompañado del rango observado M1 = 0.0952-0.2456; M0 = 0.0000, las cinco semillas y el tamaño de test. No elegiríamos la mejor semilla para anunciar desempeño. Este promedio es una descripción de estas cinco particiones; no constituye una garantía ni un intervalo de confianza. Para pedidos futuros escogeríamos otra evaluación, la temporal de C.

Pregunta 5. Relación entre positivos de test y F1¶

Cada test contiene 119 pedidos, pero en A hay entre 3 y 15 positivos, es decir, entre 2.52% y 12.61%. Con pocos positivos, un acierto o un error cambia mucho el resultado. La semilla 2026 contiene solo 3 positivos y da M1 = 0.0952; M0 = 0.0000, aunque su recall es 0.6667: encontrar dos de tres casos no evita penalizar falsas alarmas.

En estas cinco observaciones hay asociación positiva descriptiva (correlación ≈ 0.70), pero no una regla de que "más positivos siempre produce mayor F1": la semilla 0 tiene 15 positivos y la 1 tiene 12, y la 1 obtiene mayor F1. El resultado también depende de verdaderos positivos, falsos positivos, falsos negativos y de los pedidos que quedaron en train.

Pregunta 6. ¿Cambió el promedio, la diferencia entre semillas o ambos?¶

Ambos. El promedio pasa de M1 = 0.1694; M0 = 0.0000 en A a M1 = 0.1769; M0 = 0.0000 en B, un aumento pequeño de 0.0074 en F1. La amplitud entre semillas disminuye de 0.1504 a 0.0892, y la desviación muestral pasa de 0.0666 a 0.0412.

La predicción previa se cumple: B conserva 11 positivos en los 119 pedidos de cada test (9.24%), mientras A varía de 3 a 15. El 9.24% es cercano al 9.14% global; las cantidades enteras impiden una igualdad exacta. Aunque la dispersión baja, no desaparece.

Pregunta 7. ¿Stratify hace que el modelo prediga mejor?¶

Stratify cambia el reparto para conservar aproximadamente la proporción de clases en train y test. No agrega información, cambia el algoritmo ni garantiza subir F1. Ayuda a que una comparación no dependa tanto de haber reservado muy pocos positivos. En esta ejecución el promedio subió ligeramente, pero ese resultado no es una garantía del método. Tampoco corrige por sí solo el orden temporal, los restaurantes compartidos o los duplicados.

Pregunta 8. ¿Dónde sería indispensable y dónde importaría menos?¶

Es especialmente necesario en clasificación con una clase muy rara, por ejemplo fraude, fallas o calificaciones bajas, si un reparto al azar podría dejar un test sin casos de interés. Requiere suficientes ejemplos de cada clase; no crea positivos que no existen.

En un conjunto grande, equilibrado y sin dependencias temporales o por grupo, la diferencia puede ser pequeña porque el azar ya conserva proporciones parecidas. En regresión no existen clases naturales para estratificar. Si el uso es temporal o en grupos nuevos, esa estructura determina la partición, aunque las proporciones resulten distintas.

FEATURES_E = NUM_E + CAT

def nuevo_modelo_e():
    prep = ColumnTransformer([
        ('num', Pipeline([('imp', SimpleImputer(strategy='median')),
                          ('esc', StandardScaler())]), NUM_E),
        ('cat', OneHotEncoder(handle_unknown='ignore'), CAT),
    ])
    return Pipeline([
        ('prep', prep),
        ('clf', LogisticRegression(max_iter=1000, class_weight='balanced')),
    ])

def medir_e(train, test):

            'recall': recall_score(test.baja, pred),
            'n_test': len(test), 'positivos_test': int(test.baja.sum()),

Pregunta 14. ¿Cuál versión dio mejor y qué información tenía E1?¶

Empataron: E1 da M1 = 0.2295; M0 = 0.0000 y E2 M1 = 0.2295; M0 = 0.0000. El control B42 sin riesgo_rest también da M1 = 0.2295; M0 = 0.0000. La predicción de que E1 sería mayor no se cumplió y se conserva en el notebook.

E1 conoce la etiqueta baja de los pedidos de test al calcular el promedio por restaurante; incluso la etiqueta del pedido evaluado participa en el valor que se usa para predecirlo. E2 calcula ese promedio solo con train. Los promedios son diferentes, pero no producen una mejora de F1 en esta partición. El empate de una métrica discreta no elimina la fuga de E1 ni prueba que sus probabilidades sean iguales.

Una explicación plausible es que categoria_restaurante ya distingue muchos negocios de esta base, por lo que riesgo_rest aporta información parcialmente redundante. También puede cambiar probabilidades sin cambiar los aciertos que cuenta F1. No alteramos semillas ni modelos para forzar que E1 gane.

Pregunta 15. ¿Qué pasaría si E1 se presenta como resultado oficial?¶

En producción no se conocen las calificaciones de pedidos que todavía no ocurren. No se puede construir el mismo promedio usando sus etiquetas. El desempeño real puede ser menor o distinto del medido, porque se evaluó con información inaccesible al momento de predecir. En este caso no observamos una ventaja numérica de E1, pero el procedimiento sigue siendo inválido como evidencia del desempeño esperado.

E2 evita usar respuestas del test. Sin embargo, este split aleatorio todavía no reproduce fechas futuras. En una implementación real, el promedio debe usar solo calificaciones que ya hayan llegado antes de predecir. Un negocio nuevo tampoco tiene historial: map produciría un nulo y el Pipeline lo imputaría con la mediana de train, un fallback que debe declararse y evaluarse. En esta partición todos los negocios del test sí tienen historial en train.

Pregunta 16. ¿Qué otro cálculo tendría un problema similar antes de partir?¶

Calcular la mediana de imputación o la media y escala sobre toda la base antes del split haría participar al test en el preprocesamiento. La codificación de categorías también debe ajustarse con train. Estas fugas no utilizan la etiqueta como E1, pero sí información que la evaluación reservó para simular datos nuevos.

En M1 el Pipeline evita ese problema: fit aprende SimpleImputer, StandardScaler y OneHotEncoder usando solo train, y predict aplica esas transformaciones al test.

Límite adicional de E2: el promedio de entrenamiento contiene la propia etiqueta de cada fila de train. No es fuga de test, pero puede favorecer el ajuste dentro del entrenamiento. Para un modelo de producción se consideraría codificación cruzada o estadísticas históricas anteriores a cada pedido. Se conserva la fórmula de E2 solicitada por la guía, sin agregar otro experimento.

Parte F. Recomendación para Ruta Verde¶

La partición elegida debe corresponder al uso que el gerente quiera medir. Un F1 de calificaciones bajas no es una medida de error en minutos ni una probabilidad de éxito de cada pedido.

Número que reportaríamos al gerente¶

Para anticipar pedidos futuros de Ruta Verde, reportaríamos F1 M1 = 0.0370 frente a F1 M0 = 0.0000, obtenido entrenando con 442 pedidos de enero-junio y evaluando 149 pedidos de julio-agosto. Hay **14 bajas en test; el modelo solo detecta 1 (recall 7.14%) y genera 39 falsas alarmas (precisión 2.50%).

La evidencia es débil para usar el modelo como detector de bajas: superar un Dummy de F1 cero no basta para recomendarlo en operación. El gerente debe recibir esta limitación junto al número. Es una medición histórica con un único corte, no una garantía de septiembre. Antes de decidir una adopción harían falta más periodos de evaluación y objetivos de negocio para tolerar errores; esas mejoras quedan fuera de los experimentos solicitados.

13. Para llevar a la clase¶

Reflexión propuesta con apoyo de IA; revisar y discutir en el grupo.

El hallazgo que más nos sorprendió fue que agregar un promedio de calificaciones bajas calculado con toda la base no mejoró el F1 frente a calcularlo solo con train: ambas versiones dieron M1 = 0.2295; M0 = 0.0000. Nuestra hipótesis inicial era que la versión con información del test obtendría un resultado mayor. El empate nos obliga a separar dos preguntas: si el número subió y si el procedimiento es válido. La versión 1 sigue usando respuestas que no existirían al recibir un pedido, aun cuando la métrica no muestre una ventaja. No sería correcto cambiar las semillas para fabricar el resultado que esperábamos.

También fue importante observar la fragilidad del reparto aleatorio. Con el mismo modelo, A varió entre M1 = 0.0952-0.2456; M0 = 0.0000, y el test pasó de 3 a 15 calificaciones bajas. Al reservar los meses posteriores, el desempeño fue M1 = 0.0370; M0 = 0.0000, con solo una baja detectada de catorce. Esto sugiere que elegir el resultado más alto no ayuda a tomar una decisión realista.

Pregunta que nos queda: ¿se repetiría la caída temporal al evaluar varios periodos posteriores, y cuánto se explica por los tipos de pedidos frente a cambios en el servicio? El contraste entre julio y agosto invita a revisar esa cuestión, pero una sola partición no permite responderla.

Regla propuesta para Ruta Verde, en una frase y sin tecnicismos:
Antes de confiar en una predicción, probémosla con pedidos que se parezcan a los que llegarán mañana y sin mirar sus respuestas.
